## 1. 项目一句话说明

`servermonitor` 是一个 **TRSS-Yunzai 插件**，用来把多台服务器（Linux / Windows / macOS / Docker）的 CPU、GPU、内存、网络、磁盘、温度、功耗等状态，汇总渲染成一张图片，通过 `#服务器状态` 发给管理员。

采集方式为 **Push 模式**：每台被监控机器跑一个 agent，定时把 JSON 快照 POST 到 Yunzai 的一个 HTTP 路由。

---

## 2. 整体架构

```text
被监控服务器（agent.mjs）
        │  每 10s POST JSON
        │  Header: X-SM-Token
        ▼
TRSS-Yunzai :2536
  └─ Bot.express
       └─ POST /servermonitor/report   （server.js 注册路由）
              │
              ▼
         model.js  handleReport()
              │  校验 token / 限速 / 清洗数据
              ▼
         内存 state.records + data/snapshots.json
              │
              ▼
         #服务器状态 → buildStatusData() → art-template → Chromium 截图 → 发图
```

关键点：

- **不额外监听端口**，复用 Yunzai 的 `Bot.express`。
- 路由注册放在 `server.js`，并加 `Bot.express.skip_auth` / `quiet`，让插件自己的 `X-SM-Token` 生效，同时不刷日志。
- 状态数据是「内存态 + 定时落盘」，`data/snapshots.json` 只保存最近快照，用于重启后恢复。

- `public_status: true` 时任何人可看状态图。

## 6. 定时任务

定义在 `index.js` 的 `task` 数组。

> ⚠️ **踩坑记录**：`task.fnc` 必须直接传**函数引用**，不能传字符串方法名。传字符串会报 `TypeError: i.fnc is not a function`（见 commit `6a8e4ba`）。

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| servermonitor离线扫描 | `*/10 * * * * *` | 判定离线、发上下线提醒 |
| servermonitor快照落盘 | `*/30 * * * * *` | 把内存快照写入 `data/snapshots.json` |

## 7. 上报接口（最重要）

### 7.1 路由

- 方法：`POST`
- 路径：`/servermonitor/report`
- 别名：`/server-monitor/report`
- Header：`X-SM-Token: <token>`、`Content-Type: application/json`
- 体积上限：`256 KB`
- 限速：单 token+IP `60 次/分钟`；单 IP `240 次/分钟`

### 7.2 请求体 schema

```json
{
  "v": 1,
  "name": "srv-02",
  "agent_ts": 1730000000000,
  "os":     { "platform": "linux", "distro": "Debian GNU/Linux", "release": "12", "arch": "x64", "hostname": "srv-02", "uptime": 123456 },
  "cpu":    { "model": "Ryzen 7 9700X", "cores": 16, "usage": 37.5, "temp": 62, "power": null },
  "gpus":   [ { "model": "RTX 3060", "usage": 55, "temp": 65, "memUsed": 2.4, "memTotal": 12, "power": 120 } ],
  "mem":    { "used": 8.2, "total": 16, "swapUsed": null, "swapTotal": null },
  "net":    { "iface": "eth0", "rxSec": 12.3, "txSec": 4.5, "rxTotal": 1024.5, "txTotal": 512.1 },
  "disks":  [ { "mount": "/", "used": 103.5, "total": 215.4 } ],
  "load":   [ 1.2, 1.1, 1.0 ]
}
```

约定：

- `v` 必须为 `1`，否则 `422 bad schema`。
- 单位：温度 ℃、容量 GB、速率 MB/s、`usage` 百分比。
- 数值必须是 number，不要传字符串。
- `null` 表示未知；`gpus` / `disks` 可为空数组。
- `name` 会被清洗：去掉 `<>&"'`\\`，空白转 `_`，截断 32 字符。

### 7.3 token 与绑定流程

三种模式：

1. **共享 token 自动注册**
   - agent 用 `shared_token`，插件按 `body.name` 首次自动注册。
   - ⚠️ **名字必须唯一**，否则返回 `403 name conflict`。
2. **agent 生成 token，再回 Yunzai 绑定**
   - 安装器自动生成 `sm_xxx`，打印 `#服务器状态绑定 sm_xxx`。
   - 上报时插件先存 `pending`，返回 `202`，绑定后转正。
3. **Yunzai 先生成独立 token**
   - `#服务器状态添加 <名称>`，把 token 配到 agent。

### 7.4 返回码

| 状态 | 含义 |
| --- | --- |
| 200 | 成功，`{ ok:true, name, auto }` |
| 202 | 已存待绑定，返回 `bind` 命令 |
| 401 | token 无效 |
| 403 | 共享 token 名字冲突 |
| 413 | body 超过 256KB |
| 422 | schema 错误 / 空快照 / token 过长 |
| 429 | 限速或服务器数量达上限（64 台） |
| 500 | 服务端内部错误 |

## 8. agent 侧

### 8.1 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SM_NAME` | 无 | 服务器名，必须唯一 |
| `SM_TOKEN` | 自动生成 | 上报 token |
| `SM_REPORT_URL` | 无 | 上报地址 |
| `SM_INTERVAL` | 10 | 快采集周期（秒），最小 5 |
| `SM_SLOW_INTERVAL` | 30 | 慢采集周期（秒），≥ interval |
| `SM_TIMEOUT` | 5000 | 采集超时（ms） |
| `SM_DRY_RUN` | 无 | 只打印不发送 |
| `SM_ONCE` | 无 | 只上报一次 |

也支持配置文件 / 命令行参数（`agent.mjs --help`）。

### 8.2 采集策略

- **快采集**（`SM_INTERVAL`）：CPU 使用率、内存、网络速率。
- **慢采集**（`SM_SLOW_INTERVAL`）：磁盘、CPU 温度、GPU、CPU 功耗。
- 所有采集都走 `safe(fn, fallback, timeout)`，**单个指标卡住不会拖垮整体**。
- GPU 采集顺序：
  1. 直接调 `nvidia-smi`；
  2. 失败则退到 `systeminformation.graphics()`，现在会取 `utilizationGpu / temperatureGpu / memoryUsed / powerDraw`（commit `de3d164`）。

### 8.3 各平台安装位置

| 平台 | 安装目录 | 服务 |
| --- | --- | --- |
| Linux | `/opt/servermonitor/agent` | systemd `servermonitor-agent` |
| Docker | `/opt/servermonitor-docker` | docker compose |
| macOS | `/opt/servermonitor/agent` | launchd `com.servermonitor.agent` |
| Windows | NSSM 服务 | 服务名 `servermonitor-agent` |

Linux 配置文件：`/etc/systemd/system/servermonitor-agent.service`（环境变量写在 `Environment=` 行）。

## 10. 安全设计（不要回退）

| 机制 | 位置 | 说明 |
| --- | --- | --- |
| 限速 | model.js `allowReport` | 防刷 |
| body 上限 | server.js | 256KB，防大包 |
| 字段/数组上限 | model.js `sanitizeSnapshot` | disks≤16、gpus≤8、字符串截断 |
| token 定时安全比较 | `timingSafeEqualStrings` | 防时序攻击 |
| 共享 token 冲突拒绝 | `handleReport` | 防止覆盖已有服务器 |
| 配置写锁 | config.js | 防并发写坏 |
| 待绑定表上限 | `MAX_PENDING_ENTRIES=100` | 防内存膨胀 |
| 服务器上限 | `MAX_SERVERS=64` | 防滥用 |

## 11. 部署命令（新机器）

Yunzai 地址以 `http://192.168.5.88:2536` 为例：

```bash
# Linux
sudo bash <(curl -fsSL https://raw.githubusercontent.com/qsbb/servermonitor/main/scripts/install-agent-linux.sh) \
  srv-02 sm_共享token http://192.168.5.88:2536/servermonitor/report

# Docker
sudo bash <(curl -fsSL https://raw.githubusercontent.com/qsbb/servermonitor/main/scripts/install-agent-docker.sh) \
  srv-02 sm_共享token http://192.168.5.88:2536/servermonitor/report

# macOS
sudo bash <(curl -fsSL https://raw.githubusercontent.com/qsbb/servermonitor/main/scripts/install-agent-macos.sh) \
  srv-02 sm_共享token http://192.168.5.88:2536/servermonitor/report
```

Windows：

```powershell
powershell -ExecutionPolicy Bypass -File install-agent-windows.ps1 `
  -Name srv-02 -Token sm_共享token `
  -ReportUrl http://192.168.5.88:2536/servermonitor/report
```

要点：

- 安装器会**自动测速 GitHub 镜像**并选最快的。
- **重复执行同一条命令 = 更新模式**，会保留 `SM_NAME / SM_TOKEN / SM_REPORT_URL`。
- 日志：`journalctl -u servermonitor-agent -f`。

## 12. 已知问题与踩坑记录

| 问题 | 根因 | 状态 |
| --- | --- | --- |
| `i.fnc is not a function` | `task.fnc` 传了字符串方法名 | 已修 `6a8e4ba`，改成函数引用 |
| Windows 无 GPU 占用率 | 兜底只取型号和显存 | 已修 `de3d164` |
| 共享 token 上报被 403 | 多台机器用了同一个 `name` | 设计如此，需改唯一名字 |
| `#服务器状态插件更新` 401 | `origin` 带了失效认证 | 已修 `385774a`，改为直接拉官方仓库 |
| agent 重复上报被拒 | 自动注册时生成了独立 token，但 agent 仍用共享 token | **未根治**，见下 |
| CPU 功耗 / 温度不准 | RAPL 符号链接、thermal 命名差异 | 已修 |
| systemd / Docker 更新丢环境变量 | 解析未处理引号 | 已修 |

### ⚠️ 最需要关注的遗留问题

**共享 token 自动注册后，后续上报会被 403 拒绝。**

原因：`handleReport` 在共享 token 自动注册时，用 `makeToken()` 生成了**新的独立 token**写进 `config.yaml`，但 agent 端仍然用 `shared_token` 上报；下一次上报时 `resolveConfigByToken(shared_token)` 找不到对应的 server，走共享分支又发现 `name` 已存在 → 403。

现场表现：日志刷 `report rejected: shared token name conflict <name>`，服务器显示 offline。

临时解法：把 `config.yaml` 里该 server 的 `token` 手动改成 `shared_token`。

**建议的正式修法（二选一）：**

1. 共享 token 自动注册时，直接把该 server 的 `token` 写成 `shared_token`（简单，但任何持有共享 token 的机器都能冒名上报）。
2. 保留独立 token，但在 `handleReport` 里判断：若 `existingByName.note === "共享 token 自动注册"` 且请求带共享 token，则允许更新（更稳）。
