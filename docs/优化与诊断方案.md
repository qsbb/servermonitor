# Servermonitor 优化与诊断方案

> 适用仓库：`qsbb/servermonitor`
> 当前版本：`v0.1.14`
> 文档目的：把已发现的问题收敛成可执行的优化路线，并定义后续对抗性审查 / 攻击测试的执行方式。

---

## 1. 目标

1. 修复已确认的 P0 / P1 问题，保证插件在多机环境下稳定、安全、可维护。
2. 建立可复用的诊断方案，避免同类问题反复出现。
3. 用对抗性审查找出旧版本遗留漏洞和尚未被覆盖的边界情况。
4. 输出一份按优先级排序的优化清单，并尽量让每个修复都带回归测试。

---

## 2. 已确认问题总览

### P0

1. `/servermonitor/report` 无速率限制、无体积上限、字段无边界。
2. 共享 token 自动注册无服务器数量上限，可被滥用。
3. `systeminformation` 调用无超时，可能永久卡死。
4. Linux systemd 更新时环境变量读写格式不一致。
5. 双列网格会被最高卡片撑高。
6. 缺数据时 CPU / GPU 会显示成 `0.0%`。
7. Linux CPU 功耗与本机温度采集受 symlink 判断影响，可能一直为空。

### P1

1. `#服务器状态待绑定` 可在群聊中泄露完整 token。
2. 配置损坏后会静默重置并轮换 `shared_token`。
3. agent 上报的 GPU、字符串、设备名缺少边界。
4. 更新流程可能先删旧服务，失败后没有回滚。
5. Linux 内存占用包含 page cache，容易被高估。
6. 多网卡场景下网络统计不完整。
7. Docker / macOS 磁盘可能重复或为空。
8. UI 存在重复信息、截断、低对比度、空数据噪音。
9. `public_status` 默认开启，信息暴露偏多。
10. 配置写入存在并发竞态。

### P2

1. Windows 文档中的 `irm | iex` 安装方式不稳定。
2. Release exe 构建流程未随仓库保留。
3. agent 默认回传地址为 `127.0.0.1`，远端机器上会持续失败。
4. NSSM 下载源不稳定，更新时可能误删配置。
5. Docker 文档未完整说明挂载与权限。
6. 验证接口文档使用 GET，但接口只接受 POST。
7. `show_ip_in_image` 是死配置。
8. 安装脚本依赖第三方 GitHub 镜像，且未固定 commit / 校验。
9. 交互安装器对 Linux systemd 已有配置的检测不可靠。

---

## 3. 优化方案

### 第一阶段：止血与 P0 修复

1. 上报接口加防护
   - 限制单次 body 大小。
   - 对相同 IP / token 限速。
   - `name`、`mount`、`model`、`hostname`、`distro` 等字符串长度上限。
   - `disks`、`gpus` 数组数量上限。
   - pending 写入去抖，避免每次请求都全量重写。
2. 自动注册加边界
   - 服务器数量上限，默认 100。
   - 超限后拒绝并告警。
3. agent 采集加超时
   - 所有 `systeminformation` 调用包一层 `Promise.race` 超时。
   - 单项采集失败返回 `null`，不能拖垮整次上报。
4. 修 systemd 环境变量读写
   - 写入与读取使用同一套格式。
   - 更新模式下必须能读回 `SM_NAME / SM_TOKEN / SM_REPORT_URL`。
5. UI 布局修复
   - 双列模式去掉强制等高。
   - 缺数据显示为 `—`。
   - 去掉重复数字。
6. Linux 温度 / 功耗修复
   - 不依赖 `isDirectory()`，直接按路径读取。
   - thermal zone 读取 `type` 而不是 `name`。
   - RAPL 兼容 symlink。

### 第二阶段：稳定性和体验

1. `public_status` 默认改为 `false`。
2. 待绑定命令强制私聊。
3. 配置写入加串行锁。
4. 配置损坏时告警并恢复备份，不自动轮换 token。
5. 磁盘、GPU、网络、CPU 文本去重。
6. 磁盘 / GPU 名称允许换行，不再静默截断。
7. 内存口径改为更接近 `active` 的统计方式。
8. 多网卡优先聚合流量或明确选择活跃网卡。
9. Docker / macOS 磁盘去重。

### 第三阶段：部署与文档

1. Windows 安装命令改为下载后执行。
2. agent 默认地址不再回环，必须显式填写。
3. Release 构建流程恢复并固定。
4. 安装脚本减少第三方镜像依赖，或加校验。
5. 文档同步真实挂载、真实权限、真实验证方式。
6. 删除或实现 `show_ip_in_image`。

## 4. 诊断方案

### 4.1 接口层

1. 正常上报
   - POST `/servermonitor/report`
   - 携带合法 `X-SM-Token`
   - 校验 200 / 204
2. 异常 token
   - 空 token
   - 短 token
   - 超长 token
   - 未知 token
3. 异常 body
   - 空 JSON
   - 超大 JSON
   - 数组字段超长
   - 字符串超长
   - 类型错位
4. 行为边界
   - 重复 token 上报
   - 共享 token 上报
   - pending 上报
   - 并发上报

### 4.2 配置层

1. 配置损坏恢复
2. 配置并发写入
3. 共享 token 注册上限
4. 服务器改名 / 删除 / 绑定冲突
5. pending TTL 与上限

### 4.3 agent 层

1. Linux
   - CPU 使用率 / 温度 / 功耗
   - 多磁盘
   - 多网卡
   - Docker 内外差异
2. Windows
   - CPU 温度兜底
   - 多磁盘
   - 服务模式
3. macOS
   - 磁盘去重
   - GPU 兜底
4. 更新模式
   - systemd 环境变量读回
   - Windows 服务更新
   - Docker 更新
5. 异常环境
   - NFS / CIFS 卡死
   - 采集超时
   - 网络断开
   - 上报失败重试

### 4.4 UI 层

1. 1 / 2 / 3 台单列
2. 4 台双列
3. 5 台以上双列
4. 详情页
5. 离线 / 未上报 / 无 GPU / 无磁盘 / 无网络
6. 超长服务器名 / 挂载点 / GPU 名
7. 明暗主题

## 5. 对抗性审查方案

使用 3 组独立智能体，只读审查，不修改仓库。

### 组 A：安全与滥用

目标：

- 旧版本到当前版本的安全回归。
- token / pending / 共享 token / 配置写入 / HTTP 接口滥用。
- 越权、注入、重放、资源耗尽、信息泄露。

### 组 B：agent 与数据可靠性

目标：

- 采集准确性、兼容性、异常环境表现。
- 安装 / 更新 / 卸载路径。
- 旧版本遗留的数据兼容问题。

### 组 C：UI / 渲染 / 部署体验

目标：

- 渲染边界、布局、截断、空态、对比度。
- 文档与实际行为不一致。
- 旧版本残留的 UI / 部署坑。

输出统一为：

```text
[严重度] 标题
文件: 行号
描述:
影响:
复现 / 验证方式:
建议修复:
旧版本是否受影响:
```

---

## 6. 评估标准

1. P0：可造成资源耗尽、服务卡死、数据丢失、配置破坏、token 泄露。
2. P1：多机常见场景下明显影响功能、准确率或可维护性。
3. P2：部署摩擦、文档误差、体验问题。
4. P3：小缺陷或一致性改进。

---

## 7. 后续动作

1. 等三组对抗性审查结果汇总。
2. 与已有问题合并去重。
3. 输出最终优化路线。
4. 按优先级分批修复，每批附带回归验证。
